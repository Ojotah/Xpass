--------------------------------------------------------------------------------
1. PROJECT OVERVIEW
--------------------------------------------------------------------------------

What the app does
  XPass (xpass) is a desktop-oriented Flutter application that stores password
  entries inside one or more encrypted vault files on the local machine. It does
  not require a network connection for core vault operations (unlock, save,
  list accounts). Optional online checks use k-anonymity for breach detection.

Key features
  • Multi-vault: multiple encrypted files, switchable from settings or startup.
  • AES-based vault encryption with a user master password per unlock session.
  • Accounts: title, username, password, optional note; search and grid UI.
  • Import / export of vault files; vault rename and delete.
  • Breach checking (Have I Been Pwned style k-anonymity) and risk scoring
    (weak, reused, leaked heuristics).
  • Settings: theme, biometric gate, auto-lock, clipboard auto-clear.
  • Material 3 UI with light/dark themes.

Architecture used
  Clean Architecture with three main layers per feature:
    presentation (UI + Riverpod) → domain (entities, use cases, repository
    interfaces) → data (repository implementations, local IO).
  Shared code lives under lib/core (security, logging, theme, utilities).


--------------------------------------------------------------------------------
2. ARCHITECTURE EXPLANATION
--------------------------------------------------------------------------------

Layers
  presentation
    Widgets, screens, and Riverpod providers/notifiers. Maps user actions to
    use case calls and renders state. Must not embed business rules that belong
    in domain (validation exceptions for forms are acceptable at the edge).

  domain
    Entities (pure data + behavior-free models), repository abstract classes,
    and use cases (single-responsibility operations). No Flutter imports.

  data
    Implements repositories: file paths via path_provider, JSON serialization,
    and calls to core/security encryption services.

  core
    Cross-cutting: AES encryption service, breach API helper, logging, app
    theme, result/error types, clipboard helpers, password generator, etc.

How they interact
  UI → Provider/Notifier → Use case (constructed with repository impl) →
  Repository → Encryption + filesystem.
  Settings and vault metadata are persisted separately from ciphertext payloads
  where the architecture splits concerns (see local_settings_repository).

5. DATA FLOW EXPLANATION
--------------------------------------------------------------------------------

Typical unlock flow
  1. User selects vault (settings or startup list) → activeVaultId saved.
  2. LockScreen collects master password → VaultController.unlock(password).
  3. UnlockVault use case → VaultRepository.unlockVault → read file, decrypt,
     deserialize accounts list.
  4. VaultController holds unlocked accounts in memory; UI reads
     vaultControllerProvider.

Save after edit
  Add/update account in notifier → SaveVault use case → encrypt full account
  list + metadata → write file.

Settings flow
  SettingsController loads JSON → draft edited in UI → Apply saves via
  repository; themeMode propagates to MaterialApp.

Riverpod role
  Providers construct use cases and repositories (composition root at feature
  level). VaultController is a notifier for session state (unlocked, timer).

6. SECURITY DESIGN
--------------------------------------------------------------------------------

Encryption approach
  Vault file contains a JSON document with metadata and an encrypted payload
  (string). The master password never stored; decryption attempted in-memory.
  Wrong password yields WrongPasswordException (handled in UI).

Vault protection
  Files live under app documents directory (path_provider). OS-level access
  control depends on the host machine. Auto-lock clears sensitive state by
  locking the vault after idle timeout.

Breach detection
  Passwords are hashed (SHA-1) locally; only a short prefix is sent to the
  breach API (k-anonymity). Full hash never leaves the device in the request
  body as described by HIBP-style APIs.

Risk scoring
  Combines weak/reused/leaked heuristics into a 0–100 score (see
  calculate_password_risk use case and Account fields).

7. KEY FEATURES BREAKDOWN
--------------------------------------------------------------------------------

Multi-vault system
  AppVault entries in settings point to distinct .dat files. Switching vault
  clears session and navigates to LockScreen.

Import / export
  Export writes ciphertext to user-chosen path. Import copies and registers a
  new vault or overwrites with confirmation (see settings + use cases).

Breach detection
  Optional batch scan updates account compromise flags and last check time.

Risk scoring
  Displayed on cards and detail screen; progress bar color reflects severity.

Notes feature
  Optional per-account note field stored encrypted inside the vault JSON.

8. HOW TO RUN THE PROJECT
--------------------------------------------------------------------------------

Prerequisites
  • Flutter SDK (see pubspec.yaml: environment sdk >=3.3.0 <4.0.0)
  • Linux desktop enabled (for linux targets)

Debug on Linux
  flutter run -d linux

Release build (Linux)
  flutter build linux --release

AppImage (short version)
  After `flutter build linux --release`, bundle the `build/linux/x64/release/bundle`
  folder with your preferred AppImage tooling (e.g. linuxdeploy + appimagetool),
  setting the entry executable name to match your app binary, and including
  required Flutter lib/*.so dependencies from the bundle. Exact steps depend on
  your packaging script; validate on a clean machine.

Tests
  flutter test
